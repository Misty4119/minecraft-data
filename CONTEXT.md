# minecraft-data repository context

## Purpose

minecraft-data is a language-independent corpus of Minecraft Java and Bedrock Edition data consumed by protocol libraries, bots, servers, and language-specific wrappers. It is data and generator code, not a runtime package at the repository root.

The Java corpus currently includes versions through 26.3, including 26.2. The Bedrock corpus contains the editions and releases represented by data/bedrock and data/dataPaths.json. The exact supported list is the data itself, not a prose summary.

## Repository map

- data/pc/ contains Java Edition data grouped by reusable version directories.
- data/bedrock/ contains Bedrock Edition data and edition-specific protocol structures.
- data/dataPaths.json maps each edition/version/data family to a directory. Reuse is explicit and intentional.
- data/pc/common/ and data/bedrock/common/ contain shared indexes and common data.
- schemas/ contains JSON schemas and enums used by validation.
- tools/js/ contains the Node.js maintenance package, generators, protocol compiler, audits, and tests.
- doc/ARCHITECTURE.md describes the high-level model; doc/add-data-new-version.md and doc/bedrock.md describe extraction; doc/protocol.md describes protocol schema maintenance.

## Data flow

Upstream extractors and manually reviewed sources produce version data. The version tool creates the directory and path entries, generators populate registry files, and audits validate cross-file relationships. Protocol YAML is compiled to protocol.json for consumers. Consumers resolve a version through dataPaths.json and then read the selected files.

A directory is not necessarily a complete independent snapshot. When a data family is unchanged, dataPaths.json can point to an older directory. Always follow the mapping before assuming a file belongs to the requested version.

## Version facts

Java 26.2 uses protocol 776 and data version 4903. Java 26.3 uses protocol 777 and data version 5023. Keep these values synchronized with the version records and downstream protocol consumers. A version's protocol may change even when many registries are reused.

## Maintenance model

Automated generator output is preferred for blocks, items, entities, biomes, effects, enchantments, language, particles, sounds, materials, foods, collision shapes, and similar families. Protocol, windows, commands, version records, map icons, and manual corrections need source review. Every imported artifact needs reproducible provenance: source URL or jar, extractor/generator revision, extraction date, checksum, and a description of manual changes.

## Consumer relationships

node-minecraft-protocol consumes protocol descriptions and version metadata. mineflayer consumes the Node protocol and the registry data. prismarine-chunk, prismarine-item, and prismarine-physics use registry features and data selected for a version. A data change can therefore alter packet serialization, item components, chunk palettes, or physics behavior downstream.

## Failure modes and pitfalls

- Editing protocol.json directly loses the source-of-truth change on the next build.
- Adding a version only to a prose README leaves dataPaths or common indexes incomplete.
- Treating a reused directory as a new snapshot can hide a missing registry change.
- Mixing Java and Bedrock names or wire formats produces plausible but incorrect JSON.
- Large or malformed source files can exhaust memory in generators; validate inputs and avoid running untrusted code.
- Do not commit credentials, access tokens, downloaded account data, or private server logs.

## Working agreement

Use the smallest source change that explains the new data. Preserve ordering and formatting generated by existing tools. Include the affected edition, versions, data families, sources, checksums, and validation commands in the change description. See AGENTS.md for the completion checklist.


## Published versus source-tree status

The Java 26.2 and 26.3 data in this tree are newer than the current published release. A fresh npm wrapper install is not a reproducible checkout of this fork. Downstream validation uses sibling repositories and, in Mineflayer, vendor/minecraft-data; record the exact commits and provenance when reproducing a result.
